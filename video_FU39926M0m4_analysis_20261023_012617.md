Based on the official Qdrant migration tool demonstration, here is the concrete operational guidance for transferring data between instances.

### **Core Philosophy: Eliminating Snapshots**
The most significant operational shift highlighted is the move away from file-based transfers.
*   **No Snapshots Required:** The speaker explicitly states, *"The nice thing about this tool is also that it's streaming data during the migration in batches. That means you don't have to fiddle around with snapshots."*
*   **Live Migration:** Data can be migrated while the source is still active. The presenter notes, *"you can also migrate data while another data is still being inserted."*

### **What Must NOT Be Changed**
While the tool allows for architectural changes (e.g., migrating from a single node to a multi-node cluster), certain vector parameters are immutable:
*   **Vector Consistency:** According to the on-screen documentation, the **vector size** and **distance metric** must remain identical between the source and target collections.

### **Operational Steps & Commands**
To perform a migration, the following workflow is required:

1.  **Installation:** Run the migration tool as a Docker container.
    *   `docker pull registry.cloud.qdrant.io/library/qdrant-migration`
2.  **Execution:** Use the following command structure (extracting keys into environment variables for security):
    ```bash
    docker run -it \
    -e SOURCE_API_KEY=$SOURCE_API_KEY \
    -e TARGET_API_KEY=$TARGET_API_KEY \
    registry.cloud.qdrant.io/library/qdrant-migration \
    --source-url <source_url> \
    --source-collection <collection_name> \
    --target-url <target_url> \
    --target-collection <target_name> \
    --create-target-collection
    ```
3.  **Target Creation:** If the target collection does not exist, use the `--create-target-collection` flag. This ensures the target configuration (including payload indices) matches the source exactly.

### **Validation and Fault Tolerance**
*   **Automated Checks:** Before data begins moving, the tool performs several automated validations. As seen in the terminal, it checks:
    *   Compatibility of Qdrant versions between source and target.
    *   Connectivity to both gRPC endpoints.
*   **State Persistence/Offsets:** If a migration is interrupted (e.g., network failure or manual cancellation), the tool saves its progress using an "offset collection." 
*   **Resumption:** Re-running the command automatically detects where it stopped: *"The migration tool then makes sure that it will just continue where it left off."*

### **Rollback and Restarts**
*   **Full Restart:** If a clean slate is required after a failed or partial attempt, use the following flag:
    *   `--restart-migration`: This ignores existing offsets and restarts the process "fresh from scratch."

### **Security and Isolation**
*   **Credential Handling:** In the demo, the presenter isolates sensitive data by passing API keys as environment variables (`-e SOURCE_API_KEY=$SOURCE_API_KEY`) rather than hardcoding them into the command string.
*   **Network Isolation:** No direct connection between the two database clusters is required; the machine running the migration tool acts as the bridge.

### **Production vs. Demo Requirements**
While the demo shows a simple terminal-based execution, the presenter highlights a critical requirement for production environments:
*   **Network Proximity:** In a production setting, the migration tool should be run on a machine with a **fast network connection and minimum latency to both databases** to ensure optimal performance during the batch streaming process.
