# AskMukthiGuru is safe on crisis, weak on answer coverage

**Bottom line: the crisis path is strong, the question router is not "top notch", the v10 data is intact but too long and too thin to give the best answer, and the knowledge layers (OKF, Memgraph, graph expansion) are called but change nothing.** Crisis detection now has three layers, and the third (a Haiku escalation that can only raise a verdict) caught all 20 of the 24 paraphrases the rules missed. Question routing is ordered regex rules; Jev, the structured router model, is enabled in the live container yet logged 0 decisions in 24 h, so it is effectively unused. The `first_person_v10` collection is structurally sound (hash match 2,758/2,758) but 24.5% of clips exceed 60 s, 17% sit inside another clip, and the latest registered run scored 0.45 showable against a 0.85 bar. The proposed resegmentation does not yet fix this: the code in tree copies v10 points unchanged and the dry run is three hand-picked windows that produce 455-630-word clips. Wiring a "select and join verbatim clips" answer is feasible and fits invariant 15 if an LLM only returns clip ids, but it cannot help until v10 spans carry non-empty topic and entity tags. Railway staging is deployable for a diagnostic faculty demo once seven items are done; the quality bar cannot be promised. A measured demo risk: a runbook-listed "verified" question abstained 3 of 3 times on the local stack.

Labels used below: **Measured** (coordinator or note author ran it, 2026-11-16), **Inference** (reasoned from code or data), **Proposal** (not built), **Owner decision** (not resolvable by research). All numbers are local; production is unmeasured. Repo paths are relative to the repo root.

## 1. The router: crisis is strong, question routing is rules with an LLM that rarely runs

**Crisis (Measured).** Detection runs in three layers: an Aho-Corasick intake kernel (`backend/app/intake/safety_kernel.py`), the regex engine `assess_distress()` (`backend/services/serene_mind_engine.py`), and a Haiku 5.5 escalation on every message that can raise a verdict to SEVERE or CRISIS but never lower it (`backend/app/pipeline/stages/distress_stage.py:618-687`; commit `89128ddd`). On 24 crisis paraphrases the rules caught 4 and Haiku caught all 20 missed; it raised 0 false alarms on 116 ordinary questions, with a 1.1 s median (`docs/reviews/2026-11-16-railway-readiness-and-plan-review.md`, not independently re-run). The coordinator's smoke script returned the 14416 helpline 3 of 3 times, instantly. Live logs show `distress_detection` averaging 1.7 s and peaking at 5.0 s per turn, so the escalation is the most expensive pre-retrieval step. Open limits: `/api/first-person/query` calls the pipeline directly and skips `DistressStage`, so the Haiku layer does not run there (Inference, `backend/app/api/first_person.py:308`); the WhatsApp bot adds a regex failsafe but relies on `/api/chat`; the "empty inside" residual (a SEVERE message with only that signal, plus means the engine does not recognise, goes to the compassionate lane) is owner-accepted; multilingual lists are AI-authored and not native-speaker or clinician reviewed (`CLAUDE.md`).

**Question routing (Measured plus Inference).** After safety, routing is ordered regex: `OffTopicStage` (16 compiled patterns), `CasualShortCircuit`, the intent node's pre-router, and the bridge's own patterns, roughly 52 `re.compile` lines across eight files (`backend/app/pipeline/stages/off_topic_stage.py`, `backend/rag/nodes/intent.py`, `backend/rag/intent_prerouter.py`). No question-router accuracy measurement exists; the 116-question harness scores served answers, not routing decisions. **Jev correction:** the earlier review doc said the intent-node Jev flag was False. The live container shows `intent_router_jev_enabled=True` and `jev_enabled=True`, with the ambiguous-domain branch off (`intent_router_ambiguous_domain_enabled=False`). Yet the worker logged 0 Jev decisions in 24 h. The ambiguous branch has a 0.45 s budget against a measured 470-690 ms Jev latency (27 of 27 timeouts in 12 h per `docs/analysis/OUTSTANDING_ISSUES.md` A-06), and it is off anyway. The intent-node call (2.0 s timeout) is enabled but never fires: a likely reason is that the `first_person` module claims teaching turns (`backend/rag/pipeline_registry.py:88-130`) before the intent node classifies them, but this is an inference, not traced.

**What actually protects users.** A wrong route ends in an abstain, not a wrong teaching, because the post-retrieval gates (answerability, relevance judge with minimum score 3, standalone rules) decide what is served. That makes the router "adequate and safe", not "top notch". The one real routing hazard is the general-knowledge lane (A-34): invariant 21 says it is closed, but the register says it is still reachable on this posture; owner decision pending.

**Proposal.** If better routing matters, either give Jev a realistic budget (about 2 s) or run one Haiku classifier for all non-crisis turns. Both change which answers are served, so they need a registered graded run plus negative controls. Cheaper first step: add a counter for Jev decisions so "unused" is a number, not an absence of log lines.

## 2. The v10 data is intact but too long and too thin, and resegmentation is not built yet

**Measured corpus shape** (live scroll of 4,224 points: 2,758 `retrieval_child` plus 1,466 `parent_unit`, 491 videos). Median child is 24 s and 45 words; p95 is 124 s and 257 words; max 590 s. **24.5% exceed 60 s, 10.2% exceed 90 s, and only 12.5% fall in invariant 11's 18-25 s band.** 469 clips (17.0%) lie inside a longer clip of the same video; 32 share identical text; the top video holds 3.1% of spans. Speaker flag is true on 99.2% but only 731 carry a per-span verified status; `speaker_id` has four spellings. Boundary labels say "uncertain" on 23.9%; my crude head check found 18.1% starting lowercase. Host-voice leak on v10 is unmeasured (6.9% on the older collection). Structural flags do not predict showability: the recurring hub clip `UlOt31lBhLY@101` is 76 s, flagged complete and verified, and still serves four questions.

**Why answers fail (Measured, registered run `graded-9-live`).** Showable by both graders: **19/42 = 0.45** (Wilson 0.31-0.60) against bar 0.85. Of 89 answerable questions, 47 abstained: 31 were never served in any run, 9 lost a previously good answer, 7 were served but never showable. Rejected rows cite "not the question asked" (17 of 23), cut-off argument (10), dangling opener (9). Only 14 of 24 repeat-served questions got the same clip across three runs; HyDE timed out 71 of 160 times. On the older 29-question label set (LLM-authored, directional only), a relevant clip appeared in the top-10 for 79% of questions but a showable one for only 52%; the gap is boundaries and completeness. Completeness falls from 51% under 15 s to 17% over 120 s. So the failure has three coexisting parts: retrieval and coverage (about one fifth), segmentation (about one quarter), and one-clip-at-a-time judging that creates hubs. No rubric reaches both release bars on this corpus (`docs/analysis/OUTSTANDING_ISSUES.md` 9.2).

**Does the proposed resegmentation fix it? Not yet (Measured).** `backend/scripts/ops/dry_run_resegmentation.py` uses hand-selected windows with hard-coded timestamps (its own docstring says it is a demonstration, not an algorithm); its "PASS 3/3" counts a terminal period as closure. The three outputs are 630, 567 and 455 words (329, 191 and 162 s), all above the repo's own 350-word and 160 s caps (`audits/evidence/dry_run_resegmentation_results.json`). `backend/scripts/ops/build_shadow_resegmented_index.py` scrolls v10, drops event-marker clips, stamps `chunker_version="boundary_v2:rhetorical"` and upserts the same ids and vectors into `first_person_v12_shadow`: no text, boundary, embedding or hash change. It would mislabel unmodified clips as resegmented. Extending clips to close enumerations also conflicts with invariant 11 and trades "cut off" for "too long to quote" while raising hub risk (Inference). Expected gain is bounded: at most about 8 of 29 questions (relevant but not showable) benefit; retrieval misses and the 31 never-served questions are untouched.

**Proposal.** Resegment with a hard cap (about 90 s or 250 words), sentence-complete ends, and parent-level linking so a longer argument is a second verbatim clip, not a longer one. That reconciles invariant 11 with enumeration closure. Full build needs transcripts for all 491 videos (only 7 are on this machine), host-side re-embedding (invariant 18), recomputed point ids and both hashes, a new collection with v10 kept for rollback, a scorecard run, new labels on the new collection, a frozen question set and a registered run. **Owner decision:** the clip length cap, and whether invariant 11's 18-25 s is aspirational or binding.

**Proposed data targets** (my thresholds, unapproved): showable Wilson lower bound at least 0.85 on 30 or more served; clip p95 at most 90 s and max 160 s; contained clips at most 5%; same clip across three runs at least 95%; no clip serving more than three questions. Reaching 0.85 needs roughly 22 or more consecutive correct served answers, so the question-set size matters as much as the data.

## 3. OKF, Memgraph and the transcript layer are called but change nothing

**Measured trace.** A live turn runs the stage chain, then the LangGraph `first_person` node, which claims the turn and ends the graph, then `run_first_person_bridge`, then the context harness over `first_person_v10` (`backend/rag/nodes/first_person.py`, `backend/rag/graph_strategies.py:174-204`). Retrieval is dense (HyDE-substituted) plus sparse RRF in Qdrant, grouped into parent contexts. The general graph (HyDE node, legacy chat collection, OKF injection, LightRAG context) is unreachable on a claimed turn with `first_person_llm_fallback_enabled=false`.

**Why graph and OKF expansion are inert (Measured, with one inference).** Both flags are on. Graph expansion pulls neighbour concept strings from Memgraph; OKF expansion matches the query against `memory/okf/compiled.json`; both feed a `concept_ids` filter over `topic_ids`, `entity_ids` and `tags` (`backend/services/first_person_context_store.py:567-585`). On live v10, `entity_ids`, `topic_ids`, `facet_ids` and `alias_ids` exist on all 2,758 children and are **empty on every one**, and no `tags` key exists. So both filters can match nothing, and appended contexts matter only if every primary context fails the gates. The filter-semantics conclusion rests on Qdrant behaviour; no filtered query was run to prove zero hits. The one expander with real data is the TeachingUnit graph: Memgraph holds 2,760 TeachingUnit nodes with 660 `TU_PRECEDES` and 632 `TU_CONTINUES` edges, but only 6 `TU_HAS_TOPIC` and 80 Concept nodes. Whether it ever supplied a winner is unmeasured (debug-level logs only). The 6,427 LightRAG entity nodes are not reached from the first-person path.

**HyDE and latency (Measured).** HyDE is the only LLM-derived retrieval component that changes candidate order: 11 of 23 calls hit the 2.5 s timeout and fell back to the plain vector, which is the source of non-reproducible serving. For seven broken-down turns: answerability about 0.9 s, retrieval about 1.2 s, assembly about 1.5 s, total about 3.6 s (max 4.6 s). The coordinator's smoke runs on the local stack measured **7-22 s** for answered or abstained turns, so budget on the higher figure. Embeddings are not the bottleneck; LLM calls are.

**Multi-clip joining does not exist live (Measured).** The harness serves one parent context (adjacent spans of one video, joined deterministically). Facet split is dead in v10-only mode, the editorial-set selector is flag-off and production-locked, the comparative judge is off by owner rule, and `QuoteWeaver` is constructed but never called. Memory does not influence clip choice: signals only bypass the exact cache. The personalize button sends a `personalize_teaching` reference that routes to the generating graph and produces labelled prose; on the live posture it is probably inert (backend fallback off, frontend build flag unread) and no personalize turns appear in logs.

**Coverage anecdote (Measured).** "What actually creates a happy family?", listed in the demo runbook as verified, abstained 3 of 3: the relevance judge scored all 16 candidate contexts 1 or 2 (minimum 3). A different marriage question served with exact runbook wording 2 of 2. The demo runbook's verified list is stale (also: Journey 3 expects `status="direct"`, which invariant 3 says cannot occur).

## 4. Recommended design: an LLM picks and orders verbatim clips, a verifier checks, the server renders

**Evidence base.** Published graph methods gain mostly on multi-hop and "global" questions, judged by LLMs, not on verbatim-quote recall: LightRAG won 49.6-54.8% against GraphRAG on four datasets and needs under 100 tokens and one call for retrieval versus roughly 610,000 tokens for GraphRAG on one dataset ([LightRAG](https://arxiv.org/html/2410.05779)); HippoRAG 2 reports about a 7% gain on associative memory ([HippoRAG 2](https://arxiv.org/abs/2502.14802)); RAPTOR-style summaries are abstractive, which is exactly the OKF role (routing only). No source measures graph expansion on devotional transcripts. For quote integrity, Anthropic's Citations API returns `cited_text` as a parsed field rather than model output, and custom-content documents let each clip be one citable unit ([Citations docs](https://platform.claude.com/docs/en/build-with-claude/citations)); a December 2025 study recommends retrieval-centric, post-hoc-first attribution for high-stakes use ([arXiv 2509.21557](https://arxiv.org/abs/2509.21557)). Small verifiers are cheap: MiniCheck-FT5 reached 74.7% balanced accuracy against GPT-4's 75.3% at over 400 times lower cost ([MiniCheck](https://arxiv.org/html/2404.10774v2)), though instance-level agreement with LLM judges is low ([Verify with Caution](https://arxiv.org/pdf/2501.14883)). Support checking is not truth checking ([GopherCite](https://arxiv.org/abs/2203.11147)). These are benchmark numbers, not this system's false-accept rates.

**Proposal (nothing built; budgets are targets, not measurements).**

1. **Safety lane unchanged and first** (crisis, topic rail, distress).
2. **Candidate pool, parallel lanes, 300 ms hard cap:** Qdrant RRF top-30 (existing); Memgraph TeachingUnit neighbours from the top-5 clips (adjacent and continuing units, same video); OKF in-memory routing that only adds query terms or graph seeds, never text. Pool capped near 12 clips after dropping quarantined, contained, duplicate and gate-failing clips. A failed graph or OKF lane degrades to Qdrant-only (the documented Neo4j-down behaviour).
3. **One selector call** (small fast model, JSON, tight `max_tokens`) returns an ordered list of `{clip_id, role}` and at most 3 clips, replacing the separate answerability, relevance and per-clip judge calls. This is the largest latency saving and changes served answers, so it needs a graded run.
4. **Verify:** deterministic checks first (milliseconds): each quote equals store text for its `clip_id`, `source_text_hash` matches `sha256(verbatim_text)` on v10, speaker allowlist, no quarantined, duplicate or contained clip, same-video limits. Then one judge call on the assembled list: does the sequence answer the question, in an order that does not distort any quote. Fail closed on timeout, parse error or unknown id. Optional encoder NLI (LettuceDetect, already in the repo) only on connectors. Cross-quote distortion is caught only by the judge and a red-team set, not by span match.
5. **Render server-side:** quote text is injected from the store, never from the LLM; citations keep the 0.25 s playback padding (invariant 6).
6. **Stream first, join second:** serve the top-1 clip through today's gates immediately; append further quote blocks only if the stitch verifies. Worst case equals today.

**Failure modes all fall back to the current single verified clip or the static abstain; never to free-text generation.**

**Owner decision (blocking): is any LLM-written connector text allowed under invariant 15?** Safest option is none: render quotes in order with templated labels such as "Next, on the same theme" chosen from a closed set. If free connectors are allowed, they must sit outside quotes, be visibly labelled assistant voice, never use a teacher's first person, be length-capped and pass the output guardrail.

**Prerequisite the design cannot skip: populate v10 `topic_ids`, `entity_ids` and tags.** Without them the graph and OKF lanes stay inert and the pool is just Qdrant. That is an offline, reviewed enrichment with a review gate before any Qdrant write (invariant 1).

**Personalize with memories, reusing the same function (Proposal).** One `assemble(question, candidates, memory_hint=None)`: the plain path caches by `(language, message)`; the personalize path passes a short distilled user-scoped `memory_hint`, skips cache read and write, and tags the response `personalized=true`. Memory never enters the Qdrant query (shared embedding spaces leak across users: [MemLeak](https://neurips.cc/virtual/2026/169601)); it only informs selection and order and the optional opening label. Verify no memory string appears inside any quote block and extend `tests/test_cache_personalization_leak.py`. Today's personalize path generates prose, so it conflicts with this design and with invariants 15 and 21; **owner decision:** retire it in favour of the select-and-join path, or keep both.

**Graded-run requirements:** recall of showable clips with and without graph and OKF lanes on the tuning set and a held-out set; stitch acceptance and independent-judge DON'T-SHOW share against single-clip baseline; negative controls (baseline 13 of 13 out-of-corpus abstain); an adversarial set (cross-quote distortion, connector injection, transcript prompt injection); uncached p50 and p95 with the flag on and off; a default-off `Settings` flag read at the call site, with tests for both states.

## Conclusion

The central finding is a mismatch between where effort has gone and where answers are lost. The crisis layer and the gates are the hardest-won parts and they work; the knowledge layers built to improve answers (OKF, Memgraph, graph expansion, Jev) are wired but inert, because the v10 spans carry no tags to filter on and the router's LLM never gets to run. The data, not the router, sets the ceiling, and the proposed resegmentation as coded would change the label on clips without changing the clips.

The most useful next move is not another loop over the existing set. It is an enrichment and capped-resegmentation pass that makes the graph and OKF lanes real, then a select-and-join selector that returns clip ids only. That design keeps every teacher word verbatim, shortens the gate chain, and gives "personalize with memories" a safe home as a cache-bypassing second pass. It stands or falls on one owner decision: whether any connector text may be generated at all.
