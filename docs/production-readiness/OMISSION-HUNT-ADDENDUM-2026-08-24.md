# AskMukthiGuru Production Readiness
## Omission-Hunt Addendum — 2026-08-24

**Purpose.** This addendum records material omissions discovered after the expanded ruthless audit and productionization playbook were written. It is intentionally non-destructive: no production code was changed, no corpus artifact was fabricated, and no commit or push was performed for this pass.

> **Verdict remains: NOT READY for unrestricted public production.** The earlier result of **READY FOR STAGING VERIFICATION** still stands, but this pass found additional release blockers. Several are confirmed implementation or disclosure defects, not merely suggested checklist expansion.

## 1. What was checked

The omission hunt followed the repository’s evidence rules and cross-checked implementation, wiring, user-facing claims, and runtime/release implications. It read the doctrine-cache path, account-deletion Edge Function and frontend flows, Docker build context rules, native and browser push paths, both push Edge Functions, reminder behavior, authentication provider handling, store-release documentation, and the current rerun evidence. Searches were bounded to application paths and excluded virtual environments, generated caches, and unrelated build output.

The analysis distinguishes these states:

| State | Meaning in this addendum |
|---|---|
| **Confirmed defect** | The code or public documentation directly demonstrates the behavior or mismatch. |
| **Confirmed missing proof** | The feature exists, but the repository contains no adequate test or staging/device evidence for a production claim. |
| **Required verification** | A plausible risk was found, but current evidence is insufficient to call it a defect. It remains a release gate until tested. |
| **Already known, re-elevated** | The previous audit already found the issue; this pass confirms it must remain a hard gate rather than treating it as closed. |

## 5. Required verification backlog that remains open

The following were not called confirmed defects in this pass, but they are still release-gated checks because the repository evidence is incomplete:

| Area | Verification required before public traffic |
|---|---|
| **Outbound network / SSRF** | Prove web-search, URL-fetch, media, and provider egress use scheme/host allowlists, redirect blocking, private-network rejection, DNS-rebinding defenses, response-size/time limits, and audit-safe error handling. Existing provider-specific checks do not automatically prove every outbound path. |
| **Edge-function CORS and auth** | Verify `delete-my-account` and push functions reject unauthorized origins and malformed/replayed authorization, while preflight behavior works for the owned web origin. `Access-Control-Allow-Origin: *` on an admin/cron push function should be treated as a design decision, not assumed safe. |
| **Cron/webhook authentication** | Inventory every scheduled or webhook-triggered function, rotate shared secrets, add replay/idempotency protection, and prove unauthorized invocation cannot trigger deletion, push, ingestion, or maintenance. |
| **Email operations** | Test password-reset, reactivation, deletion-support, and notification email deliverability, bounce handling, abuse/rate controls, domain authentication, mailbox ownership, and privacy-safe content. |
| **Third-party processors** | Reconcile actual OpenRouter, Sarvam, Google, Ollama-hosted, Firebase/FCM, APNs, Supabase, Sentry, OTel/Jaeger, and hosting flows against Privacy/Terms, DPAs, retention, data residency, and “no external training” claims. |
| **Backups and disaster recovery** | Prove encryption/key ownership, retention/deletion semantics, restore into an isolated environment, point-in-time recovery, and rollback of both database and vector/graph state. A backup that cannot satisfy the deletion contract remains an unresolved privacy question. |
| **Age, crisis, and accessibility** | Verify age/under-13 wording, crisis disclaimers and escalation localization, permission dialogs, push/reminder controls, screen-reader behavior, reduced motion, long translated strings, and mobile safe-area behavior across the supported locales. |
| **Incident operations** | Conduct alert, escalation, support-SLA, user-notification, kill-switch, and post-incident communication drills. Ensure edge-function failures and silent push no-ops are observable. |
| **Domain/deep-link ownership** | Prove every push deep link, OAuth redirect, support URL, marketing URL, and email link resolves to an owned HTTPS/app-link target in each environment. |

## 6. Updated priority order

The immediate engineering order is:

1. **Keep public traffic blocked** until the missing approved artifacts and benign-chat transport failure are closed.
2. **Hard-disable or redesign `DoctrineCacheStage`** so a configuration toggle cannot bypass retrieval and verification.
3. **Choose and implement the deletion contract**, then correct every public claim before store submission.
4. **Fix Docker build-context determinism** and add a dirty-worktree contamination test.
5. **Choose one push architecture**, fix service-worker scope, define token lifecycle and payload policy, and add real browser/device/cron evidence.
6. **Separate web beta from store launch** and complete Apple, Firebase, support, privacy, deletion, content-rating, and TestFlight gates.
7. **Resolve the auth allowlist policy** and test every provider/redirect path.
8. **Close the verification backlog** for egress, cron, email, processors, backups, accessibility, and incident operations.
