# Retrieval-Gap Fix Plan (2026-09-06, session 2)

Source: live run of the Step-29 offline retrieval-quality harness against production Qdrant (`spiritual_wisdom_contextual`), 25 stratified golden queries. Result: recall@1=0.32, recall@5=0.48, recall@10=0.48 (zero gain 5→10 — worse than the typical 5-12 point improvement literature shows at that range), MRR=0.39. 13/25 queries scored recall@10=0.0; 12/25 scored 1.0; **zero partial hits** — a bimodal pattern that pointed straight at root cause rather than generic "ranking is imperfect."

Root-cause breakdown of the 13 zero-recall failures, verified against live Qdrant (not inferred):

- **5 failures — genuine corpus gap.** `doctrine_four_secrets-000`, `doctrine_founders-021`, `doctrine_founders-026`, `doctrine_manifest-042`, `doctrine_deeksha-060` all cite `The_Four_Sacred_Secrets.pdf` as their sole correct source. Confirmed via direct Qdrant scroll: **zero points** with that `source_url` exist in `spiritual_wisdom_contextual`. The PDF was never ingested (or was ingested into a different/stale collection).
- **8 failures — real retrieval-ranking gap, not a corpus gap.** `doctrine_soul_sync-086`/`-087` and 6 others cite YouTube videos confirmed present in the collection with real chunk counts (`o_eg6YTifRE`: 5 chunks, `JRX5W9AhWoA`: 10 chunks) — the content exists but never surfaces in the top 10 hybrid-retrieval results for these specific queries. Both verified examples are short, specific-technique-name queries ("What is the purpose of the Humming step in Soul Sync?", "What do we visualize during the Golden Light step?") — a known dense-embedding weak spot for short queries carrying a unique proper-noun technique name with little surrounding context to embed against.

**Not in scope for this plan**: re-enabling Guru Brain. It is a genuine product-vs-safety tension (see prior session note) — the live `ToneAdapterStage` was deliberately made a no-op because post-hoc answer rewriting after citation attachment risks altering claims or losing attribution, which directly conflicts with the anti-hallucination guarantees this whole audit protects. That is a product decision for a human to make explicitly, not something to silently flip because the code exists. If you want it revisited, say so and I'll scope it as its own plan with the safety tradeoff spelled out.

## Step 1 — Resolve the unlicensed `The_Four_Sacred_Secrets.pdf` labels without ingesting the PDF

**Intent**: Confirmed via direct Qdrant scroll that zero points exist for this source in `spiritual_wisdom_contextual`, despite it being cited as ground truth for 5/25 (20%) of the golden retrieval set. The repository's content-rights invariant prohibits restoring or ingesting that PDF: its rights basis is unconfirmed and the source was deliberately removed from git history.
**Implemented control**: the corpus-publication manifest now makes source-rights approval an explicit, hashed prerequisite for publishing an index contract. The retrieval-drift checker reports missing labelled sources read-only, so the five labels cannot silently look like a retrieval regression.
**Required human decision**: either obtain and record an approved rights basis before any separate ingestion work, or relabel these queries to approved first-party/public sources. Do not use the PDF as a shortcut to improve a benchmark score.

## Step 2 — Debug the 8 real retrieval-ranking failures per-query

**Intent**: Content demonstrably exists in Qdrant for these 8 queries but never surfaces in top-10. Unlike Step 1, this is not a corpus gap — it needs per-query investigation: pull the actual embedding-similarity scores between the query and the known-relevant chunks (not just top-10 results) to see how far outside the cutoff the correct chunk actually sits, and check whether the chunk's text contains the query's key technique-name terms at all (a chunking/context-header issue) or whether it's purely a dense-embedding semantic-gap issue (an embedding-model limitation).
**Out of scope**: changing the embedding model or retrieval architecture preemptively; for each of the 8 queries, log the correct chunk's actual rank (not just whether it's in top-10) and its raw similarity score, and the sparse (BM25) contribution the RRF fusion assigned it — this tells you whether the fix is "the sparse signal should have weighed more for proper-noun/technique-name queries" (a tunable RRF-weighting question) or something deeper (chunking split the definition away from the technique name).

## Step 3 — Verify the golden dataset's `correct_chunks` counts have not drifted from re-ingestion

**Intent**: The golden dataset (`evaluation/datasets/golden_retrieval_v1.json`) stores a `correct_chunks` **count**, not a Qdrant point index, alongside `correct_sources`. If the corpus was re-chunked or re-ingested since this dataset was built (plausible given `contextual_reingest.py`'s documented backfill from `spiritual_wisdom` to `spiritual_wisdom_contextual`), the count and source-level all-terms coverage can drift, silently invalidating labels even where the source video is present.
**Implemented control**: `backend/benchmarks/check_golden_retrieval_drift.py` scrolls the selected collection read-only, verifies every labelled source exists, recomputes source-level `must_mention` coverage with the same normalization as the builder, and reports count drift. It exits non-zero with `--fail-on-drift`, which is appropriate only for an explicitly approved staging corpus.
**Out of scope**: rebuilding the golden dataset from scratch. If drift is found, flag the items for relabeling rather than silently trusting stale labels.

## Step 4 — Re-run the full harness after Steps 1-3 and record the delta

**Intent**: Get the actual before/after recall@k/precision@k/MRR numbers once the corpus gap is closed and any ranking issues from Step 2 are addressed, as the real evidence of improvement rather than assuming Step 1 alone fixes everything.
**Out of scope**: none — re-run `benchmarks/offline_retrieval_quality.py --live` against the same 25-query stratified sample and diff against the baseline captured this session (recall@1=0.32, recall@5=0.48, recall@10=0.48, MRR=0.39).

## Step 5 — Root-cause and fix the LettuceDetect heuristic-path regression (blocks enabling the real model)

**Intent**: `settings.lettucedetect_enabled` defaults `False`; the *real* RAGTruth-trained ModernBERT faithfulness classifier (`KRLabsOrg/lettucedect-base-modernbert-en-v1`) has never actually run in this codebase — every faithfulness check this session used the weaker heuristic cosine-similarity fallback in `backend/services/lettuce_detect_service.py`. Research (vLLM's HaluGate blog) suggests a comparable classifier should run at ~12ms vs. the heuristic's observed 700-3300ms, and a purpose-trained classifier should also out-accuracy a cosine-similarity proxy at the exact task it's named for — this is very likely the single highest-leverage latency **and** accuracy lever in the whole codebase.
Session 3 found the actual compatible dependency versions (isolated-venv proven, not guessed): `numpy>=2.2.2,<2.3` (resolved 2.2.6) + `pyarrow>=16.0.0,<17.0` (resolved 16.1.0) + `datasets>=2.19.2,<3.0` (stayed at already-installed 2.19.2) + `lettucedetect>=0.2.2` (resolved 0.2.3) import cleanly together and resolve the original `numpy.core.multiarray failed to import` / pyarrow ABI break from the first attempt (see `lessons.md` L-DOCKER-8). Applying this combo to the real `backend/.venv` then broke 4 tests in `tests/test_lettuce_detect_service.py` — the *heuristic* fallback path (mocked embedder, no real model involved) started returning `is_faithful=False` where `True` was expected, plus an unexplained "Fetching 7 files" HuggingFace network call appeared during a test that should never touch the network. Not root-caused; reverted fully (`pip install -r requirements.txt` restores `numpy==1.26.4`/`pyarrow==14.0.2`, `pip uninstall lettucedetect rag-fact-checker easydict`). See `lessons.md` L-DOCKER-13 for the full account.
**Out of scope**: shipping any dependency version bump without first fixing this regression; changing `requirements.txt` at all until the 4 test failures are understood. Concrete next actions: (a) bisect which single package version change (numpy 2.x numeric/casting behavior vs. a `huggingface_hub` version bump changing local cache-trust behavior) causes the heuristic path's cosine-similarity math to flip its verdict — run each of the 4 failing tests with only `numpy` bumped (pyarrow/datasets/lettucedetect held at current pins) to isolate whether numpy alone is sufficient to reproduce it; (b) find what triggers the "Fetching 7 files" network call despite `lettucedetect_enabled=False` — grep for any HF `from_pretrained`/`snapshot_download` call reachable from `LettuceDetectService.__init__` or from a *different* component sharing the same test process (embedder singleton, reranker) that might now behave differently with a newer `huggingface_hub`; (c) once both are understood and fixed, re-run the full suite, confirm all 4 tests pass, confirm `import rag.graph_strategies` still clean, then flip `settings.lettucedetect_enabled=True` in a scoped test/staging environment and A/B the real detector's latency + faithfulness-verdict agreement rate against the heuristic on a fixed set of past chat transcripts before touching the production default.

## Step 7 — Investigate faithfulness-verification non-determinism (L-DOCKER-10)

**Intent**: the identical question ("What is the beautiful state?"), same infra, same non-cached fresh calls, returned `verified:true/grounded` once and `verified:false/abstained` once. Root cause hypothesis (not yet confirmed): Sarvam's `generate_answer` call runs at non-zero temperature, so the generated answer text differs run to run, and the heuristic faithfulness check's cosine-similarity score swings across its threshold for different phrasings of an equally-correct answer.
**Out of scope**: lowering the faithfulness threshold to "fix" this (that trades away the one property — no hallucination — the verification stack protects). Concrete next actions: (a) confirm the hypothesis by logging the actual generation temperature used for `generate_answer` and re-running the same question 5-10 times, checking whether faithfulness score varies with answer-text variance; (b) if confirmed, evaluate whether a lower (not zero — some phrasing diversity is fine) temperature for factual/doctrine-tier generation reduces variance without hurting answer quality, informed by the same "temperature 0.2-0.5 for grounded generation" literature already cited in this doc's session-2 entry; (c) this is likely to improve, not just explain, once Step 5's real LettuceDetect model replaces the heuristic — a purpose-trained span-level classifier should be less sensitive to surface-level phrasing differences than raw cosine similarity.

## Step 8 — A/B the regenerate-before-rewrite flag before flipping its default

**Intent**: `settings.rag_regenerate_before_rewrite` (default `False`, added this session, commit `8fa28aee`) lets a faithfulness/persona-violation correction retry generation against the same already-graded context instead of paying for a full CRAG-style re-retrieval — research-backed (Self-RAG fixes reasoning over evidence; CRAG fixes the evidence itself; a pure generation-faithfulness failure is Self-RAG's problem, not CRAG's), tested in isolation (5 new tests in `tests/test_graph_strategies.py`), but **never run against live traffic**.
**Out of scope**: flipping the default without measurement. Concrete next action: enable the flag in a staging/test environment, send the same question set used in Step 6/L-DOCKER-9 through both flag states, and compare (a) latency on the correction path specifically (`node_timings` for requests where `needs_correction` was true) and (b) whether the regenerate-only path actually recovers a faithful answer as often as the full rewrite path does, or whether it just fails faster without fixing anything — only promote the default to `True` if both hold.

## Step 9 — Host capacity ceiling (not fixable in this repo)

**Intent**: a genuine `MemoryError` under concurrent deep-tier load (see `lessons.md` L-DOCKER-11/L-DOCKER-12) traced to a real, non-code capacity ceiling: a 16GB Mac running Docker Desktop's VM overhead, this app's ~2.9GB of deliberately-coexisting models, the full container stack, and a second independent AI coding session's own heavy processes, all at once.
**Out of scope for code changes**: this is not something `docker-compose.yml` or application code can fix — raising this container's own memory limit further just relocates the ceiling onto something else on the same host. Documented here only so it isn't rediscovered from scratch: either get more RAM, or don't run two full AI-coding-session stacks against this repo on the same machine at the same time, before trusting any load-test result as representative of real production headroom.
