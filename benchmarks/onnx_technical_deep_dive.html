▶ Architecture 1. BGE-M3 Model Architecture

BGE-M3 (BAAI General Embedding — Multi-Lingual, Multi-Functionality, Multi-Granularity) is built on XLM-RoBERTa (Cross-lingual Language Model — Robustly Optimized BERT Approach), a 560M-parameter Transformer encoder pre-trained on 2.5TB of CommonCrawl data across 100+ languages.

PropertyValue
Base architectureXLM-RoBERTalarge
Parameters~560M (Encoder only, no decoder)
Hidden dimension1024
Transformer layers24
Attention heads16
Max sequence length8192 tokens (configured)
Vocabulary250,000+ WordPiece tokens (multilingual)
Pre-training data2.5 TB CommonCrawl (100+ languages)

Three output heads (single forward pass):

HeadOutput shapePost-processingPurpose
dense_vecs (batch, 1024) L2-normalize (unit vector) Semantic similarity search via HNSW index in Qdrant
sparse_vecs (batch, seq_len, 1) ReLU → filter unused tokens → L1-normalize Lexical/BM25-style keyword matching via Qdrant inverted index
colbert_vecs (batch, seq_len, 1024) Per-token L2-normalize Token-level late interaction reranking (not yet used in cp1 pipeline)
Key insight: BGE-M3's three-head design eliminates the need for a separate sparse encoder (e.g., BM25, SPLADE) and a separate ColBERT model. One forward pass produces all three representations, enabling true hybrid search (dense + sparse) with optional ColBERT reranking. This is unique among open-source embedding models.
▶ Quantization 2. Optimum O2 + QOperator INT8 Quantization

The gpahal/bge-m3-onnx-int8 model uses Optimum O2 quantization with QOperator (QOp) — ONNX Runtime's built-in INT8 quantized operator kernels.

Quantization pipeline:

1. Export BGE-M3 (PyTorch) → ONNX fp32 (O2: `optimization_level=99`, all transforms)
2. Calibration: 100 samples from WikiText-2 (typical, exact dataset unknown)
   → collect activation ranges (min/max per tensor)
3. Symmetric per-channel quantization of weights:
   W_int8 = clamp(round(W_fp32 / scale), -128, 127)
   scale = max(abs(W_fp32)) / 127
4. Asymmetric per-tensor quantization of activations:
   A_uint8 = clamp(round((A_fp32 - zero_point) / scale), 0, 255)
   scale = (max(A_fp32) - min(A_fp32)) / 255
   zero_point = round(-min(A_fp32) / scale)
5. QOperator nodes inserted: MatMul → QMatMul + DequantizeLinear
   (dequant happens inside the kernel — weights stay INT8 in memory)
ParameterWeightsActivations
SchemeSymmetricAsymmetric
GranularityPer-channel (output dim)Per-tensor
Range[-128, 127] (int8)[0, 255] (uint8)
Memory reduction4x (32b → 8b)4x (32b → 8b)
Information loss (SNR)~24 dB (1.5% RMSE typical)~22 dB (2% RMSE typical)
Why symmetric for weights, asymmetric for activations: Weight distributions are approximately symmetric around zero (pre-trained Transformer weights have zero-mean distribution). Activations after ReLU/GELU are strictly non-negative, so asymmetric quantization captures the full dynamic range without wasting half the quantization levels on negative values that never occur.

QOperator execution model:

INT8 MatMul = input(uint8) @ weight(int8)  (INT8 dot product)
Output = DequantizeLinear(MatMul, scale_w * scale_a, ...)
→ fp32 output for next layer (residuals, LayerNorm, etc. stay fp32)

The dequantization from INT8 → fp32 after each MatMul adds ~5-10% overhead vs pure INT8 compute, but is necessary because LayerNorm, GeLU, and residual addition require fp32 precision. This is the same trade-off as GPTQ/AWQ.

▶ Runtime 3. ONNX Runtime Session Configuration

Session creation:

session = ort.InferenceSession(
    model_file,
    providers=["CPUExecutionProvider"],
)
# No explicit session options — using defaults:
#   inter_op_num_threads: 2 (parallelism across graph nodes)
#   intra_op_num_threads: auto (logical cores)
#   graph_optimization_level: ALL (applied at session creation)
#   execution_mode: SEQUENTIAL (sequential within a node, parallel across nodes)
SettingValueRationale
Execution providerCPUExecutionProvider No GPU on Railway; CPUExecutionProvider is the most mature, stable provider for x86-64 Linux
Graph optimizationALL (level 99) Constant folding, node fusion, layout optimization — applied once at session creation, zero runtime overhead
intra_op_num_threadsAuto (vCPU count) ONNX Runtime manages its own thread pool; OMP_NUM_THREADS=1 in env to avoid oversubscription
inter_op_num_threads2 (default) BGE-M3 graph has limited node-level parallelism; 2 threads is sufficient
Execution modeSEQUENTIAL Nodes within the same graph partition run sequentially; parallelism is across partitions
Why not set explicit thread counts? For batch_size=1 (the common case in chat), MatMul dimensions are small (1024x1024 or 4096x1024). Intra-op threading doesn't help much — the overhead of threading synchronization can exceed the parallel speedup. ONNX Runtime's auto-detection handles this well. The OMP_NUM_THREADS=1 env var prevents PyTorch (if still loaded) from fighting for cores.
▶ Pipeline 4. Tokenization & Post-Processing

Tokenization (HuggingFace AutoTokenizer with BAAI/bge-m3 config):

# Tokenizer config
model_max_length = 8192
padding = True (pad to longest in batch)
truncation = True (clip at model_max_length)
return_tensors = "np" (numpy arrays for ONNX runtime)

# ONNX inputs
input_ids: int64[batch, seq_len]
attention_mask: int64[batch, seq_len]

# ONNX outputs
ort_out[0]: dense_vecs    — float32[batch, 1024]
ort_out[1]: sparse_vecs   — float32[batch, seq_len, 1]
ort_out[2]: colbert_vecs  — float32[batch, seq_len, 1024]

Post-processing (dense):

dense = ort_out[0]  # raw, NOT normalized
dense = dense / np.linalg.norm(dense, axis=1, keepdims=True)
# → L2 unit vector for cosine similarity in Qdrant HNSW index

Post-processing (sparse — custom extraction):

sparse_raw = ort_out[1]          # (batch, seq_len, 1)
unused_tokens = {cls, eos, pad, unk}

for row_idx, token_ids in enumerate(input_ids):
    weights = sparse_raw[row_idx, :, 0]
    result = defaultdict(int)
    for w, tid in zip(weights, token_ids):
        if tid not in unused_tokens and w > 0:
            key = str(tid)
            if w > result[key]:          # Max-over-tokens (duplicate token IDs from WordPiece)
                result[key] = w
    sparse_weights.append(dict(result))  # → [{token_id: weight}, ...]
Important: The ONNX model does NOT apply L2 normalization internally — unlike the FlagEmbedding/BGEM3FlagModel Python path which normalizes before returning. The encode_batch() ONNX path must normalize dense vectors in Python (dense / np.linalg.norm(dense)). The post-processing for sparse vectors mirrors the FlagEmbedding approach: ReLU (keep only positive), filter special tokens, and take max-weight per token ID (handling WordPiece sub-token duplication).
▶ Concurrency 5. Thread Safety & Concurrency Model
ComponentThread-safe?Locking
ONNX InferenceSessionYes No lock needed for session.run(). ONNX Runtime uses internal thread pool, thread-safe by design.
Tokenizer (HuggingFace)Yes Tokenizer is stateless between calls — pure functions over input text.
Embedding cache (LRU)Yes Cache uses cachetools.LRUCache — thread-safe for concurrent get/put.
Model loading (_ensure_encoder)Yes Double-checked locking via self._lock (threading.Lock). Only one thread loads.
Inference (encode_batch, encode)Conditional Uses self._inference_lock (RLock). Python GIL serializes tokenization + post-processing, but ONNX session.run() releases the GIL.
FastAPI async handlersYes All _async wrappers use asyncio.to_thread() — GIL escape via thread pool.
Concurrent query flow (production): Under load with WEB_CONCURRENCY=1 (single FastAPI process), multiple concurrent chat requests are interleaved on the event loop. When encode_batch_async() is called, it dispatches to a background thread via asyncio.to_thread(). The ONNX session.run() call releases the GIL, allowing other Python work (tokenization for another request) to proceed in the main thread. However, concurrent session.run() calls share the inter_op thread pool, so heavy load may cause queuing at the ONNX layer.

Why fp32 variance is 40x higher (cold):

  • PyTorch JIT compilation: First few inferences trigger JIT kernel compilation (even on CPU, PyTorch uses kernel fusion). Each compiled kernel adds 5-50ms one-time cost.
  • Caching memory allocator: PyTorch's caching_allocator calls mmap/munmap during warmup. First inferences after model load trigger allocation spikes of 20-80ms.
  • ATen thread pool: torch.set_num_threads(1) does not prevent lazy initialization of the ATen thread pool on first parallel operation. Adds ~50-100ms.
  • CPU frequency scaling: macOS ramps CPU from low-power to performance mode during the first seconds of heavy compute.

Why ONNX variance is low:

  • Graph optimizations pre-applied at session creation — no JIT.
  • ORT uses a simple arena allocator with pre-allocated buffers for common sizes.
  • INT8 integer ops are faster and more predictable than fp32 with denormals.
  • 4x smaller weight reads — memory-bound MatMuls are less sensitive to cache misses.
Production implication: For a long-running server, warm numbers (fp32 P95 ~35ms, ONNX P95 ~16ms) are representative. But after idle periods or container restarts, cold-start penalty matters. Railway's single-replica deployment with no keep-warm means every request after a period of inactivity pays the cold penalty. ONNX INT8 reduces this from 186ms to 26ms — a 159ms improvement on first-query-after-idle.
▶ Roofline 7. Memory Bandwidth & Roofline Model

Roofline analysis of BGE-M3 (dense-only, single forward pass):

Weight read (fp32):  560M params x 4 bytes    = 2,240 MB
Weight read (INT8):  560M params x 1 byte     =   560 MB
FLOPs:               560M x 2 (MatMul mul+add) = 1.12 GFLOPs (single fwd)
Total with bias:     ~2.24 GFLOPs

Apple M-series memory bandwidth: ~60-100 GB/s

fp32 arithmetic intensity:  2.24 GFLOPs / 2,240 MB = 1.0 FLOPs/byte → MEMORY BOUND
INT8 arithmetic intensity:  2.24 GFLOPs / 560 MB   = 4.0 FLOPs/byte → BALANCED

fp32 roofline:  100 GB/s / 4 bytes x 2 = 50 GFLOPs ceiling
                Achievable: 2.24 / (2,240 / 100) = ~100ms (empirical: 33-185ms)

INT8 roofline:  100 GB/s / 1 byte x 2 = 200 GFLOPs ceiling
                Achievable: 2.24 / (560 / 100) = ~25ms (empirical: 16-26ms)
Key insight: BGE-M3 is memory-bandwidth-bound on CPU at fp32 precision. The weights (2.24 GB) must be read from DRAM for every forward pass, and they're so large that even modern caches (L2: 256KB/core, L3: 8-16MB) can't hold them. INT8 reduces the weight traffic 4x, moving the model from "memory bound" (1.0 FLOPs/byte) to "balanced" (4.0 FLOPs/byte) on the roofline. The 4x memory reduction translates directly to 4x theoretical speedup, matching the empirical 7x cold / 2-4x warm results. This is also why thread configuration matters less for INT8 — the bottleneck is no longer compute.

Risk profile: Low. The change is toggle-controlled (single env var), validated against 380 queries + 143 retrieval evaluations, and has automatic fallback to smaller models if the ONNX path fails. Rollback is a one-line change in .env + container restart. The ONNX path is also independent of the HF cache — it uses snapshot_download(local_dir) to a temp directory, so HF cache corruption (the root cause of the July 2026 embedding incident) cannot affect it.
▶ Limitation 11. ColBERT Reranking — cp1 Limitation

Current state: The ONNX model outputs colbert_vecs (token-level 1024-d vectors) at ort_out[2], but the pipeline does not use them. Active retrieval path: dense-sparse hybrid with RRF fusion.

Planned implementation (NumPy MaxSim):

def colbert_maxsim_rerank(
    query_colbert: np.ndarray,    # (q_tokens, 1024) L2-normalized
    passage_colbert: np.ndarray,  # (p_tokens, 1024) L2-normalized
) -> float:
    similarity = query_colbert @ passage_colbert.T  # (q, p) cosine matrix
    max_per_token = np.max(similarity, axis=1)       # best match per q token
    return float(np.mean(max_per_token))             # overall relevance

# Integration: RRF + ColBERT weighted fusion
# score = 0.6 * rrf(dense_rank, sparse_rank) + 0.4 * colbert_score
CostValue
FLOPs per candidate32 (query tokens) x 128 (psg tokens) x 1024 = 4.2M
FLOPs for top-20~84M
Estimated latency (CPU)~3ms
ColBERT storage (100k passages)100k x 128 x 1024 x 2 (fp16) = ~25 GB

Why ColBERT reranking matters for AskMukthiGuru: User queries about meditation are often fuzzy paraphrases of doctrine passages. Dense-sparse hybrid captures semantic + lexical matches, but ColBERT's token-level MaxSim can match "how do I calm my mind" to "technique for mental stillness" at the sub-phrase level — something dense cosine similarity misses. For the doctrine domain where seekers ask the same question in many ways, ColBERT provides the best retrieval precision. This is a formal release blocker, not a casual TODO.
