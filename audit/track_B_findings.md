**Status: COMPLETE for the critical isolation test (PASS — no leak found). Second Brain vault is completely non-functional in this environment (config defect, not a leak).**

`POST /api/chat` (authenticated or anon) → `PipelineCoordinator` → `context_engineer` stage calls `prepare_user_memory` (per root `CLAUDE.md`, canonical memories skip anonymous identities) → `generate_answer` → response's `evaluation_trace.memory_used` flag. **Launch Blocker:** YES (blocks any real dev/QA verification of the authenticated product surface; also a data-hygiene risk — see Root Cause)

  VITE_SUPABASE_PUBLISHABLE_KEY=sb_publishable_xiLP47LDiH7JKMf1GfLhng_6MZfd8JC
  ```
- `/Users/harshodaikolluru/Public/askmukthiguru-8119b0e8/backend/.env`:
  ```
  SUPABASE_URL=http://host.docker.internal:54321
  PUBLIC_SUPABASE_URL=http://127.0.0.1:54321
  ```
  (`ozmjeuqbholoxypfxixb` is the project ref root `CLAUDE.md` itself documents as the **production** Supabase project, in its "Production Supabase readiness audit" section.)
- Reproduction: created `harshakolluru1+audita9182@gmail.com` via `POST http://127.0.0.1:54321/auth/v1/signup` (local Supabase) — succeeded, auto-confirmed. Attempted sign-in with the identical email/password through the actual `/auth` UI at `http://localhost:8080` → `"Incorrect email or password. Please check and try again."` (screenshot evidence captured during session).
**Root Cause:** `src/integrations/supabase/client.ts` reads `import.meta.env.VITE_SUPABASE_URL` / `VITE_SUPABASE_PUBLISHABLE_KEY`, sourced from `.env.local`, which points at the production Supabase project. Even if a real production-registered user did sign in through the UI (getting a JWT signed by production Supabase), the backend's `get_current_user_from_supabase` validates against the **local** Supabase's keys, so that token would very likely fail backend-side validation too — meaning the fully-authenticated path (Second Brain, canonical memory CRUD, profile, admin) is plausibly broken end-to-end for anyone testing against this exact local-docker + local-Vite combination, not just for the test accounts created here.
**User Impact:** In this specific dev/audit configuration, no real user can complete signup+login and then successfully call an authenticated backend endpoint through the actual app UI. Every authenticated feature (Second Brain, canonical memory management, Settings/Profile, Admin) is untestable through the UI as configured. If this env split is unintentional (e.g., a leftover `.env.local` from testing against prod), it also means local development against this branch may be silently exercising the **production** user database — a data-hygiene / accidental-prod-write risk worth confirming is intentional.
**Required Fix:** Decide and document the intended local-dev auth target. If local Supabase is meant to be canonical for dev (as the task brief and root `CLAUDE.md`'s "Gotchas" section both assume — "Running the backend on the host... Export `SUPABASE_URL=http://localhost:6333`... needs URL overrides"), update `.env.local`'s `VITE_SUPABASE_URL`/`VITE_SUPABASE_PUBLISHABLE_KEY` to the local Supabase values (`http://127.0.0.1:54321` + the local anon key from `backend/.env`'s `SUPABASE_ANON_KEY`). If pointing the frontend at production is intentional for some reason, document it loudly in `CLAUDE.md` and make sure the backend can validate production-issued JWTs (shared JWKS/issuer allowlist), or the auth flow is fundamentally non-functional for local development.
**Regression Test:** An E2E test (Playwright, `tests/e2e/`) that signs up a fresh account through the UI, confirms it lands on an authenticated page, then calls one authenticated backend endpoint (e.g., `GET /api/memory/canonical`) and asserts `200`, not `401`.

### AMK-B-002 — Backend crashes under moderate concurrent load; auto-restart is unreliable
**Severity:** CRITICAL
**Launch Blocker:** YES
**Evidence:**
- First crash: `docker logs mukthiguru-backend` captured a native-code Python `faulthandler`-style multi-thread stack dump (ONNX/torch/lettucedetect frames — `transformers/models/modernbert/modeling_modernbert.py`, `lettucedetect/detectors/transformer.py`, `services/embedding_service.py::_encode_batch_onnx`) immediately followed by `Running initialization as root... / Starting server with WEB_CONCURRENCY=1 workers... / Dropping privileges to appuser...` — i.e., the process died and the container restarted itself (`RestartCount=1` at that point). In-flight `POST /api/memory/canonical` and `GET /api/memory/canonical` calls made during the restart window returned `500 {"error":"An internal error occurred", "message":"We encountered an issue processing your request. Please try again.", "error_id":"err_..."}`.
- Contemporaneous log evidence of resource pressure: `services.reranker_service` — `"CrossEncoder primary failed, falling back to FlashRank: [ONNXRuntimeError] : 6 : RUNTIME_EXCEPTION : ... std::bad_alloc"`.
- Second crash (a few minutes later, while driving the actual chat UI): all in-flight `/api/chat`, `/api/chat/stream`, `/api/chat/title` requests failed client-side with `net::ERR_CONNECTION_RESET`. `docker ps -a` showed `mukthiguru-backend  Exited (137)` — SIGKILL exit code, consistent with an OS/cgroup OOM kill. `docker inspect` showed `RestartCount=1` still (not incremented further) and the container **stayed in the `Exited` state** for the remainder of that check — despite `docker-compose.yml` declaring `restart: unless-stopped` for the backend service (`memory: ${BACKEND_MEMORY_LIMIT:-6G}` limit). It did not come back on its own; recovery required a manual `docker start mukthiguru-backend`.
- `mukthiguru-autoheal` (the compose stack's watchdog, labeled via `labels: - "autoheal=true"` on the backend service) produced **no log output** in the relevant window (`docker logs mukthiguru-autoheal --since 10m` was empty) — it did not intervene, likely because it watches Docker's HEALTHCHECK "unhealthy" status transitions, not a fully-`Exited` container.
- Ambient load context: concurrent `/api/chat?wait=true` traffic (question about "the 1987 stock market crash and Wall Street trading strategies") was already hitting the backend from an unrelated source before and during this audit's own requests — i.e., this is not purely a self-inflicted load spike, though the audit's own concurrent job-queue polling and chat calls contributed.
**Root Cause:** The reranker/lettucedetect ONNX+torch stack allocates enough native memory under concurrent load to either segfault/abort the process (first incident) or trigger an OS-level OOM kill (second incident, exit 137) inside the 6G container memory limit. `docker-compose.yml`'s `restart: unless-stopped` policy did not reliably bring the container back after the harder (SIGKILL/exit 137) failure mode within the observation window, and the `autoheal` sidecar does not cover this failure mode either (only watches HEALTHCHECK, not container liveness).
**User Impact:** Under real concurrent traffic (the exact scenario a "10k Tier" or even modest "1k Tier" pilot launch would see per root `CLAUDE.md`'s own SPOF policy table), the entire backend can go down hard and stay down until a human manually restarts the container — a full outage, not a graceful degradation, for every user (not just the ones whose requests triggered it).
**Required Fix:** (1) Root-cause and cap the reranker/lettucedetect memory usage under concurrency — likely needs a request-level concurrency limiter specifically around the ONNX/torch verification path (the existing `chat_backpressure` admission control reports `max_concurrent: 8` in `/api/health`, but that evidently was not enough to prevent this). (2) Add a container-level watchdog that also restarts on `Exited`/non-running state, not just Docker HEALTHCHECK "unhealthy" — either extend `autoheal`'s config or add a cron/systemd-level supervisor, since `restart: unless-stopped` alone was observed to not self-heal reliably from this failure mode on this host. (3) Consider `WEB_CONCURRENCY` / worker-count tuning and an explicit `mem_limit` closer to observed steady-state (docs cite "2.57GiB steady / 4.55GiB peak of 6G" — this incident suggests peak can exceed that under load).
**Regression Test:** A load test (`backend/scripts/load_test.py` or `scripts/benchmarks/load_test.py`, both already in the repo) run at realistic concurrency (6-10 simultaneous `/api/chat` calls sustained for several minutes) as a CI/pre-release gate, asserting the container's `docker inspect --format '{{.State.Status}}'` stays `running` throughout and `/api/health` stays `200` at the end.
**Verification:** Re-run the same load test after the fix; confirm no crash and that `/api/health` never drops below `ready:true` for an extended window (e.g., 15 minutes at the target QPS from the SPOF table).

### AMK-B-003 — "Tell me more" / follow-up quick-actions inject the entire previous answer as literal prompt text
**Severity:** MEDIUM
**Launch Blocker:** NO
**Evidence:** After receiving a "Beautiful State" answer and clicking the "Tell me more" quick-action chip, `document.querySelector('textarea').value` (captured live via JS in the browser) contained:
```
Tell me more about this: The Beautiful State is a profound inner state characterized by gratitude, calm, peace, and love. So when you're hurt, you dissolve your hurt, you move to love. When you're angry, you dissolve your anger, you move to peace." This state transcends external achievements and focuses on inner transformation, leading to lasting happiness and harmony.

_2 lines were set aside — the teachings here did not carry them._

i.e., the entire prior answer **including the internal redaction meta-commentary sentence** was quoted back as the "user's" next message.
**Root Cause:** The quick-action handler (likely in `src/components/chat/InlineActions.tsx` or `ChatComposer.tsx`) builds the follow-up prompt by templating the full previous-answer text rather than a short reference/intent (e.g., a message ID + a short instruction the backend expands server-side, or just the short label itself).

**Required Fix:** Send a short, clean intent (e.g., `"Tell me more about: <short topic phrase>"` or a structured `{action: "elaborate", message_id}` payload) instead of the full verbatim answer text with internal metadata sentences included.
**Regression Test:** A frontend unit/component test asserting the composer value (or the outgoing chat payload) after clicking each quick-action chip does not contain the literal string `"_2 lines were set aside"` or exceed some reasonable character budget (e.g., 200 chars).
**Verification:** Click each of "Tell me more" / "Explain simply" / "How relates to me" after a redacted answer and confirm the resulting prompt is short and free of internal system text.
